# Data handling (KVKK / GDPR)

This page explains, for the Turkish Personal Data Protection Law (KVKK, Law
No. 6698) and the EU General Data Protection Regulation (GDPR), what Raggie
stores, what leaves your server in each configuration, how long data is kept
and how to delete it. It describes the
software, not legal advice: you (the organization running Raggie) are the
**data controller**, and you decide which optional features to enable.

See also: [security-model.md](security-model.md) (threat model) and
[configuration.md](configuration.md) (every setting).

## 1. What Raggie stores, and where

| Store | What is in it |
|---|---|
| **Postgres** | Organizations, teams, workspaces and memberships; users (email, name, job title, department, manager, phone, location, timezone, locale, argon2id password hash, role); sessions (hashed refresh tokens); invites; documents (filename, size, status, folder, object key, `deleted_at`); conversations and messages (question and answer text, cited source excerpts in `messages.sources_json`, model, evaluation scores, feedback); per-user memory facts (`user_memory`); scheduled tasks and notifications; skills; integrations (credentials encrypted with `INTEGRATION_ENC_KEY`); system settings and branding; the audit log. |
| **Object store** (S3 API; SeaweedFS bundled) | The original uploaded files, under `uploads/<workspace_id>/…`. |
| **Qdrant** | One point per document chunk: the chunk **text**, its dense and sparse vectors, and payload such as `workspace_id`, `document_id`, filename and heading path. |
| **Valkey** (Redis-compatible) | Login-lockout counters, rate-limit counters, chat idempotency keys (10 min), the query-embedding cache (24 h, keyed by a hash of the query), and Streams used as the internal event bus (document and chat events). |
| **Logs** | Container stdout. No prompt, answer or document text is logged (see §5). |

## 2. What leaves the server

The table lists every outbound data flow in the code and whether it is on by
default.

| Feature | Destination | What is sent | Default |
|---|---|---|---|
| Chat answers | Your LLM provider (`LLMAAS_BASE_URL`, or the endpoints in `LLM_MODEL_PROFILES_JSON`) | System prompt (workspace prompt + skill + RAG template); up to 16 previous messages of the conversation; retrieved document chunks (12 by default); the question; images attached to the message (only for models listed as vision-capable). When enabled: the persona block (name, title, department, locale, tenure, manager name) and up to 20 memory facts; web-search evidence; MCP tool results. | **On** (required) |
| Widget chats | LLM provider | As above, without persona and memory. | On for EXTERNAL workspaces |
| Answer evaluation | LLM provider | The answer and the context it was based on (faithfulness judge). | On |
| Memory extraction | LLM provider | The user's message and the answer, to extract durable facts. Internal users only. | Off: the workspace's memory switch is off by default (the global `MEMORY_ENABLED` kill switch is on) |
| Skill generation, schedule parsing, scheduled tasks, deep-research planning | LLM provider | The user's description, request text, task prompt, or question. | On when used |
| Embeddings — local mode | Nothing leaves the server | — | **Default** |
| Embeddings — cloud mode | The configured embeddings provider | Document chunks at ingest time and every search query. Sparse (BM25) vectors are always computed locally. | Off (opt-in, experimental); see [embeddings.md](embeddings.md) |
| Remote reranking | The configured rerank provider (Cohere, Voyage or TEI) | The query and the candidate chunks. | Off (local reranker by default) |
| Web search | Brave Search API | The question (or LLM-generated sub-queries in deep-research mode), result count, country and language. | **Off**, globally (`WEB_SEARCH_ENABLED=false`) and per workspace |
| Web page reading | The websites in the search results | HTTP GET from your server's IP with user agent `RaggieBot/1.0` (top 8 results, 30 in deep research). | Only when web search is on |
| MCP tools (Jira) | `mcp-atlassian` container → your Jira | Tool arguments generated by the model (for example a JQL search). | **Off** (`MCP_ENABLED=false`) |
| Model download | Hugging Face | Nothing by default: the models are baked into the image and the gateway runs offline (`HF_HUB_OFFLINE=1`). Only if you opt into download-on-first-start ([embeddings.md](embeddings.md#image-variants-and-offline-mode)) are model files fetched once. Hugging Face telemetry is disabled. | Off by default |
| Update check | `RELEASE_MANIFEST_URL` | A plain GET. | Off (empty URL) |
| Product telemetry | — | None from Raggie's services: Next.js telemetry is disabled and no analytics SDK is included. The bundled Qdrant's anonymous usage reporting is disabled (`QDRANT__TELEMETRY_DISABLED=true`) in Docker Compose, the Kubernetes manifests and both Helm profiles. | — |

### Controller / processor guidance

- Every hosted provider you configure (LLM, cloud embeddings or rerank, Brave,
  Atlassian) acts as a **processor** for the data in the table above. For
  personal data you need an appropriate legal basis, a data processing agreement,
  and — for transfers outside Türkiye or the EEA — a transfer mechanism (for
  example standard contractual clauses or the KVKK transfer rules).
- Tell your users what is processed. The persona block and memory facts are
  personal data.

### Fully on-premises configuration

Nothing leaves your network when:

1. the LLM is self-hosted behind an OpenAI-compatible API (vLLM, Ollama, TGI…),
   configured via `LLMAAS_BASE_URL` or `LLM_MODEL_PROFILES_JSON` (see
   [llm-providers.md](llm-providers.md));
2. embeddings and reranking stay in **local** mode (the default), and model
   files are baked into the image or pre-downloaded;
3. web search is off (`WEB_SEARCH_ENABLED=false`, the default);
4. MCP is off (`MCP_ENABLED=false`, the default).

For demos with no model at all, the `mock` compose profile provides a
deterministic offline LLM.

## 3. Retention

There are **no automatic retention or expiry jobs** today. Conversations,
messages, the audit log, documents' database rows and notifications are kept
until someone deletes them. Defining and enforcing a retention period is the
operator's responsibility (for example a scheduled SQL job; see the deletion runbook in §4).

Short-lived data with built-in expiry:

| Data | Lifetime |
|---|---|
| Query-embedding cache (Valkey) | 24 h |
| Chat idempotency keys (Valkey) | 10 min |
| Web page cache (edge memory) | 30 min |
| Widget tokens | 30 min (`WIDGET_TOKEN_TTL_SECONDS`) |
| Access / refresh tokens | 8 h / 30 days |

The event-bus streams in Valkey are not trimmed yet; trimming is planned.

## 4. Deletion

| What | How | What actually happens |
|---|---|---|
| A conversation (by its owner) | Delete in the chat history | Hard delete of the conversation and its messages. |
| All of a user's conversations | "Clear history" | Hard delete of all of that user's conversations. |
| Widget conversations | — | No deletion path in the UI or API yet. |
| A document | Delete in the knowledge base | The row is soft-deleted (`deleted_at`) and a purge event is published. The ingestion worker then deletes the document's **Qdrant points and the stored object**, with retries. The database row (including the filename) is kept. |
| A folder | Delete folder | Every document in the subtree is deleted as above. |
| An archived document | Archive | Removed from search; the stored object is **kept**. |
| A user (deactivation) | Admin → users → deactivate | Sessions are revoked; data is kept. |
| A user (hard delete) | SCIM `DELETE /scim/v2/Users/{id}` only | Removes the user, memory, sessions, scheduled tasks and notifications. Their conversations stay with `user_id` set to NULL. |
| Memory facts | Account settings → memory → clear | Deletes **all** of the user's memory facts. Deleting a single fact is not implemented. |
| Notifications | Notification inbox | Owner can delete each one. |
| A workspace or an organization | — | Not implemented yet (planned). |

**Important:** answers keep the excerpts they cited. `messages.sources_json`
stores the snippet text of each source, so text from a deleted document can
still appear in old conversations until those messages are deleted.

### Runbook: erasure request for a person

The following is an **illustrative outline — adapt it to your schema version
and test on a copy before use.** Take a backup first and keep a record of the
request.

1. Find the user: `SELECT id, org_id FROM users WHERE email = 'person@example.com';`
2. Revoke access: deactivate the user in the admin console (this revokes every session).
3. Delete their conversations and memory:

   ```sql
   -- ADAPT BEFORE USE
   BEGIN;
   DELETE FROM messages WHERE conversation_id IN
     (SELECT id FROM conversations WHERE user_id = :user_id);
   DELETE FROM conversations WHERE user_id = :user_id;
   DELETE FROM user_memory WHERE user_id = :user_id;
   DELETE FROM notifications WHERE user_id = :user_id;
   DELETE FROM scheduled_tasks WHERE user_id = :user_id;
   COMMIT;
   ```

4. Remove the account itself, either via SCIM `DELETE /scim/v2/Users/{id}`
   or by deleting the `users` row after the steps above. Consider whether audit
   log entries (`audit_log.actor_user_id`, `target`) need to be kept for your
   legal obligations or pseudonymized.
5. If the person **appears inside documents**, delete or replace those
   documents in the knowledge base. That purges their chunks from Qdrant and the
   file from the object store. Then search `messages.sources_json` and
   `messages.content` for remaining excerpts.
6. Backups: the data stays in backups until they rotate out. Document your
   backup retention period.

## 5. Logging

- The edge logs requests as method, path, status, duration and request id.
  Questions are logged only as a length and a sha256 prefix; tests enforce
  that question text never reaches the logs.
- No service logs prompt text, answer text or document content.
- The edge propagates `X-Request-Id` (or generates one).
- The first-run setup token is logged **once**, in plaintext, when the control
  plane generates it at first boot (so the operator can complete onboarding).
  Set `SETUP_TOKEN` yourself to avoid this.
- When a document purge fails, the worker logs the event payload, including the
  object key (which contains the original filename).

## 6. Personalization and memory

| Feature | Global switch (default) | Per-workspace switch (default) | Who |
|---|---|---|---|
| Personalization — persona block in prompts | `PERSONALIZATION_ENABLED` (on) | `personalization_enabled` (**off**) | Internal users only |
| Memory — durable facts extracted from chats and injected into later prompts | `MEMORY_ENABLED` (on) | `memory_enabled` (**off**, also for workspaces created before 0.1.0) | Internal users only |

To turn them off for the whole deployment, set `PERSONALIZATION_ENABLED=false`
and/or `MEMORY_ENABLED=false`. Users can view and clear their memory in account
settings, even while memory is off. Turn memory on per workspace in *Admin →
Workspaces*; the toggle is locked when `MEMORY_ENABLED=false`.

## 7. Widget visitors

- `embed.js` sets no cookies and uses no localStorage or sessionStorage; the
  widget token lives in memory for the page's lifetime.
- A widget conversation is bound to the token's random session id, not to a
  person. It still stores the questions and answers, which may contain personal
  data the visitor typed. Mention this in your website's privacy notice.
- Widget chats never use personalization, memory or MCP. They can use web
  search if it is enabled on that workspace.
